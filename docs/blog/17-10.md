# Fast scrolling and long lists

Until now, I reserved a 2 MB block of the PSRAM for the music index and copied
the whole thing into it at boot. That doesn't work with large collections, so
let's improve it.

This problem is tied to the fast scrolling one. Until now I had two scrolling
speeds: one row per click, and one page per click when the wheel spins fast. On
laaaaarge lists, it took ages to scroll all the way down. Let's fix that on the
way, and make the index structure handle fast scrolling well.

The short version:

- The index is now **one file on the SD card**, `openpod/index.pack`. The
  firmware reads it 4 KB at a time, when it needs it, and keeps the recent
  pages in PSRAM. The library is bounded by the card, not by the PSRAM.
- Boot no longer copies anything: **3.1 s with 100,000 tracks**, against
  5.6 s with 6,000 before.
- Fast scrolling now **jumps from letter to letter**: the faster you turn, the
  bigger the jump. One turn of a flick goes from A to T in a 100k-track list.
- The bench did most of the work: the AI drove the device over serial,
  measured, and found two bottlenecks I would never have guessed.

## The old index

- One file per map: Artist->Album, Album->Tracks, Track->Path, etc.
- One file for the trie (the search structure).
- All files copied into PSRAM at startup, one after the other.
- Nothing checked the end of the 2 MB region. Past 8 MB, the chip's addresses
  wrap around onto the audio buffer.

### Sizes depending on the collection size

On my real library (1,658 tracks, 28 GB of music), the index takes 568 KB:
about **340 bytes per track**. The search trie is 60% of it, the paths 20%:

| File | Size |
| --- | --- |
| `music_index.bin` (search trie) | 343 KB |
| `path_index.bin` | 118 KB |
| `track_index.bin` (titles) | 46 KB |
| relations, durations, track→album/artist… | 61 KB |

On the generated bench dataset (`npm run bench -- prepare --tracks N`), I get:

| Tracks | Index | Search trie | Paths | Titles | Fits in 2 MB? |
| --- | --- | --- | --- | --- | --- |
| 1,658 (my library) | 568 KB | 343 KB | 118 KB | 46 KB | ✅ |
| 20,000 | 5.5 MB | 2.7 MB | 1.6 MB | 0.6 MB | ❌ |
| 100,000 | 25.1 MB | 11.2 MB | 8.0 MB | 3.1 MB | ❌ |

So the 2 MB region held about **7,300 tracks**. A 128 GB card of 4-minute MP3s
is around 21,000 tracks. And the boot time grew with the library: 13.9 s at
20,000 tracks, just to copy the index.

## The new index

### One pack file

The syncer now writes every table, and the trie, as sections of a single
file:

```
"OPIX" | u16 version | u16 0 | u32 count | {u32 id, u32 offset, u32 length} * count
then the sections, 16-byte aligned
```

The podcast tables get their own `podcasts.pack`, since they're rebuilt
separately. At boot, the firmware only opens the pack and reads its section
table. Nothing is copied.

While I was at it, the tables changed to be cheap to read from the card:

- **Ids are dense** (0..count, already in alphabetical order), so the tables
  are indexed by id directly. The old string tables had an array of ids that
  was always 0, 1, 2… and every name lookup did a 15-step binary search in it.
  Gone.
- **Relations store where each source's targets start**, instead of how many
  there are. To find artist #3,000's tracks, the old code added up the counts
  of the 2,999 artists before it: thousands of reads.
- **New letter tables**: for the full lists (artists, albums, genres, tracks),
  where each 1-, 2- and 3-letter prefix starts. That's for the fast
  scrolling, below. They're tiny: 13 KB for 100,000 tracks.

The pack ends up a bit smaller than the old files: 562 KB for my library,
24.2 MB at 100k tracks (from 25.1).

### A page cache in PSRAM

The firmware reads the pack through a cache (`src/storage/PageStore.h`):

- The 2 MB region now holds the podcast listening state (128 KB) and 480
  slots of 4 KB.
- A page is a 4 KB block of the pack file, so small sections share pages.
- Each page can only go into one *set* of 4 slots (4-way set associative).
  That way there's no hash table to keep in RAM: the whole cache bookkeeping
  is 2.1 KB of RAM, and the RAM is the scarce resource (3.5 KB free at
  runtime).
- Within a set, eviction is CLOCK (second chance): a page used since the hand
  last passed it stays.
- A miss reads the page from the card in one go, then calls `audioYield()`,
  so a cold read never starves the audio fifo.

An old card (indexed by a previous syncer) shows "Library needs a re-sync".

### What a page miss costs

That's where the bench was precious. The first version used 8 KB pages, read
512 bytes at a time through a stack buffer. On the device:

| Version | One page miss | Slowest search keystroke (cold) |
| --- | --- | --- |
| 8 KB pages, 512-byte reads | 26 ms | 564 ms |
| + 4 KB reads (borrowed buffer) | 22 ms | 469 ms |
| + pack written contiguous | 13 ms | 340 ms |
| 4 KB pages, one read each | **6.5 ms** | **179 ms** |

Three things were going on:

1. **Each SD read has a fixed cost.** 16 reads of 512 bytes cost much more
   than one of 8 KB. I have no RAM left for a big buffer, but the audio buffer
   already has a 4 KB one for its SD → PSRAM chunks. Both only use it within
   one call of their own, so the page cache borrows it.
2. **The pack was fragmented on the card.** The syncer rewrote it in place,
   so the filesystem first reused the old file's clusters, then went
   elsewhere. Every seek then walks the cluster chain: 9 ms of a 22 ms miss.
   Now the syncer writes a new file and renames it over the old one. The
   firmware warns at boot when the pack isn't contiguous.
3. **A search touches pages all over the pack**: trie nodes, results, then
   the names and artists of up to 100 hits. It reads a few bytes from each
   page, so smaller pages are cheaper.

With the 26 ms misses, a cold keystroke took ~550 ms. Typing a few of them in
a row right after a track started drained the audio buffer: **1,515
underruns** in the search scenario. Now it's 0.

## New fast scrolling

The idea is to jump from letter to letter. At the fastest level, a click jumps
from first letter to first letter. A bit slower, from 2-letter prefix to
2-letter prefix (AB → AC). Then 3 letters (ABA → ABB). Then back to row by
row. And the overlay shows the letters you're jumping by.

### The speed

The wheel's speed is measured over the last 250 ms of clicks, and picks a
tier:

| Clicks per second (24 per turn) | One click jumps to |
| --- | --- |
| under 12 | the next row |
| 12 | the next 3-letter prefix |
| 25 | the next 2-letter prefix |
| 40 | the next first letter |

- The tier goes up at once, but only goes down below 70% of its threshold, so
  it doesn't flicker.
- Turning back, or pausing 300 ms, starts over at row speed: you usually turn
  back to aim precisely.
- Short lists don't get the fine prefixes: under 150 items, only first
  letters; under 1,500, up to 2 letters.

A first version counted the clicks in the window and divided by 250 ms. At 8
clicks per second, timing jitter at the window's edge read it as 8 or 12, so a
slow turn kept slipping into 3-letter jumps (628 rows instead of 24!). It now
divides the clicks by the time they actually took.

All the thresholds can be changed live over the serial (`#scrollcfg t3=12
t2=25 t1=40 …`) to tune them by feel.

### The jumps

Every list is in alphabetical order (the syncer sorts the ids the ICU way:
case and accents ignored, spaces and punctuation before letters), so a prefix
is one contiguous block. For the full lists, the next block's start comes from
the letter tables. For scoped lists (an artist's albums, an album's tracks),
the firmware reads names: it gallops forward (+1, +2, +4…) until the prefix
changes, then bisects. That's a dozen reads even in a 5,000-row block.

The prefix ("key") of a title is computed the same way on both sides, by
`scroll_key` in the syncer and `fastScrollKey` in the firmware, with shared
test cases:

- a title that doesn't start with a letter is `#` (they all sort first)
- then letters uppercased, and anything else a space: `A Day` → `A D`

### On the device

On the 100,000-track list, one full turn of the wheel:

| Turn | Speed | Result |
| --- | --- | --- |
| 3 s | 8 clicks/s | 24 rows |
| 1.2 s | 20 clicks/s | 3-letter jumps, from the top to "Anz…" |
| 0.7 s | 34 clicks/s | 2 then 1 letter, to "K…" |
| 0.4 s | 60 clicks/s | first letters, to "V…" |

## Usage of the new benchmark capabilities

It has been super useful! I can let the AI take full control of the device:
it flashes the firmware, drives the wheel with the virtual finger over serial,
and measures at the same time. That gives reliable comparisons between
versions, and makes it very easy to see the bottlenecks. The page miss table
above is one afternoon of it.

New serial commands:

- `#scrollcfg` tunes the speed tiers.
- `#cache` gives the page cache counters (hits, misses, time spent reading
  the card).
- `#state` now shows the overlay's letters and the highlighted row's key.
- Tier changes are echoed as `#ev fast l=<letters> v=<clicks/s>`.

The e2e tests check the tiers too: a steady turn jumps by 3 letters, a flick
lands on the start of a first-letter block, and turning back goes row by row.

Along the way it also found two bugs in the bench itself:

- **The output the board prints while nobody reads the port loses bytes.**
  An answer could then end up glued to a truncated log line
  (`…max20#ok state …`), and the host never saw it.
- **The bench answered a button gesture as soon as its last keyframe
  played**, about 20 ms before the wheel's debounce reported the release. So
  the tests saw a `down` without its `up`.

## Results

The 100,000-track card against the previous run (6,000 tracks, everything in
PSRAM):

| | Before (6k tracks) | Now (100k tracks) |
| --- | --- | --- |
| Boot to ready | 5.6 s | **3.1 s** |
| Library index load | 2.4 s | 0.17 s |
| Search index load | 2.0 s | 0.008 s |
| Fast scroll burst (p95) | 67 ms | 39 ms |
| Underruns, all scenarios | 0 | 0 |
| Slowest search keystroke (cold) | 45 ms | 179 ms |
| Open a list (p95) | 865 ms | 1.0 s |
| Scroll one row (p95) | 63 ms | 76 ms |

The last three are the price of reading from the card: the first time you
type a letter or open a list, its pages come from the SD. The next step is to
load the most used parts of the index (artist and album names, the letter
tables, the top of the trie) into the cache while the device is idle after
boot.
